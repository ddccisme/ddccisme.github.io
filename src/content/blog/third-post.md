## 为什么放在一起讲

做大数据售前，几乎每个方案的起点都是向客户解释：
「你们的核心交易库不能直接拿来跑报表」。
这句话背后的就是 OLTP 和 OLAP 的分野——这是数据类方案的第一课。

## 一句话版本

- **OLTP**（On-Line Transaction Processing，联机事务处理）：管「记账」——
  每一笔订单、每一次转账，讲究快和准
- **OLAP**（On-Line Analytical Processing，联机分析处理）：管「盘账」——
  全年销售趋势、用户画像，讲究算得全、算得快

## 对比速查表

| 维度 | OLTP | OLAP |
| ---- | ---- | ---- |
| 典型场景 | 下单、支付、扣库存 | 报表、多维分析、BI 大屏 |
| 操作类型 | 增删改为主（写多） | 查询为主（读多、大扫描） |
| 单次操作涉及数据 | 几行 | 几百万到几十亿行 |
| 关心什么 | 延迟（毫秒级）、一致性 | 吞吐（扫描速度）、聚合性能 |
| 建模范式 | 3NF 实体关系建模 | 维度建模（星型/雪花） |
| 数据新鲜度 | 实时 | T+1 或准实时（取决于同步链路） |
| 典型产品 | MySQL、PostgreSQL | ArgoDB、ClickHouse、Doris、Greenplum |

## 为什么不共用一套

一个经典反问：「MySQL 也能跑 group by，为什么要单独建数仓？」

数据量小的时候确实可以。但当交易表涨到亿级：

1. **大扫描会拖垮交易**——一条几个月数据的聚合查询占满 IO，下单接口跟着抖
2. **分析建模不适配**——业务库按 3NF 拆成几十张表，分析师 join 到怀疑人生
3. **历史数据会被清理**——交易库只留热数据，分析要的是全量历史

所以成熟的做法就是**读写分离到极致**：交易库专注交易，
数据按 ETL/实时同步链路进数据仓库/数据湖，分析在数仓里做。

## 售前话术提炼

> 「不是您的数据库不好，而是它天生为交易而生。分析是另一门手艺，
> 需要专门的引擎——这就是我们方案里数据平台层的价值。」

## 一句话记忆

**OLTP 是收银台，OLAP 是后面的账房。收银台要快，账房要算得清。**
