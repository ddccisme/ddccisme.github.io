## 概念演进：一部「先分后合」的历史

讲湖仓一体（Lakehouse）之前，得先知道它是怎么来的——三个阶段：

**第一阶段：数仓（1990s-）**

结构化数据进仓，维度建模，SQL 分析。
问题：只吃结构化数据，成本高，历史包袱重。

**第二阶段：数据湖（2010s）**

什么数据都往湖里倒（日志、图片、音视频、半结构化），
存算分离，成本大幅下降。
问题：湖变成了「数据沼泽」——没有治理、没有事务、查询性能差。

**第三阶段：湖仓一体（2020s-）**

把仓的能力（事务、治理、高性能 SQL）搬到湖上，
在一个体系里同时支持 BI 分析和 AI/ML 训练。
所谓「一份数据，多种负载」。

## 一张表分清三个概念

| 能力 | 数据仓库 | 数据湖 | 湖仓一体 |
| ---- | -------- | ------ | -------- |
| 支持的数据类型 | 结构化为主 | 全类型 | 全类型 |
| 事务 ACID | ✅ | ❌（裸对象存储） | ✅（表格式层实现） |
| SQL 性能 | 强 | 弱 | 强 |
| 成本 | 高 | 低 | 低（存算分离） |
| 治理/血缘 | 强 | 弱 | 强 |
| AI/ML 友好 | 一般 | 好 | 好 |

## 关键技术：表格式（Table Format）

湖仓一体的核心是**表格式**——在裸文件（Parquet）之上加一层元数据协议，
让「一堆文件」表现得像「一张表」：

- 提供事务：并发读写不脏读
- 提供 schema 演进：加列不改历史文件
- 提供 time travel：查历史版本
- 代表：Iceberg、Hudi、Delta Lake

> 记忆点：**表格式 = 给数据湖发了「户口本」**。有了户口，湖里的数据才能被
> 治理、被事务保护、被高性能查询。

## 客户最容易混淆的三个问题

1. **「我们已经买了存储，还要湖仓干什么？」**
   存储只是「湖底」，湖仓一体卖的是湖上的「航运系统」——表格式、
   引擎、治理。光有湖底，船开不起来。

2. **「直接全上湖，还要仓干什么？」**
   高频报表、强一致 ETL 场景，成熟数仓的稳定性依然有优势。
   好架构是「湖仓协同」而非二选一。

3. **「湖仓一体是不是就是把两个产品连起来？」**
   不是简单拼接，关键是**同一份数据**上跑分析和 AI，
   避免数据在「湖→仓」之间来回搬运的一致性和成本问题。

## 一句话记忆

**仓管结构化、湖纳万物、湖仓一体 = 湖的成本 + 仓的能力。**
